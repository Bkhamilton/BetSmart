# Supabase Authentication

Supabase Auth is the source of identity, credentials, and session state. SQLite
keeps its integer `Users.id` for existing foreign keys and associates each
authenticated account through the unique `Users.cloudUserId` value.

## Configuration

- Set `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_API_KEY` to the
  existing primary project's URL and public anon/publishable key. Never ship a
  service-role key or database password in the app.
- Enable email/password sign-in in Supabase Auth. Configure its redirect URL
  allowlist for the app's `myapp://auth/callback` and
  `myapp://reset-password` links, along with the exact development-client
  links generated by Expo when testing locally.
- Keep the confirmation and recovery email templates pointed at the redirect
  URLs above. The app handles verification and recovery links through Expo
  Linking; a stale or malformed link displays an error and must be requested
  again.
- The app stores native Auth sessions in Expo SecureStore, split into bounded
  chunks for platform keychain value limits. Web uses AsyncStorage. On native
  startup, a legacy session stored under the previous AsyncStorage key is
  moved into SecureStore.
- PR #53 already created `public.bs_profiles` and its owner-only RLS policies.
  Do not rerun that migration; reconcile its CLI migration history before a
  future `supabase db push`.

## Local database migration and legacy data

The versioned SQLite auth migration removes the plaintext `Users.password`
column and the obsolete `UserSessions` table while preserving local user row
IDs and all existing betting/history rows. Legacy user rows are retained
without a `cloudUserId`; they are not authenticated or attached to a Supabase
account by matching email or username. That old history therefore remains
unavailable until a separately reviewed migration is designed.

New local account rows are created or refreshed only after Supabase returns an
authenticated session and the corresponding `bs_profiles` row is retrieved or
created by Auth UUID. A profile is never replaced during login. Duplicate
usernames, profile access failures, and interrupted initialization are surfaced
and can be retried; a registration blocked by a username conflict can be
retried after choosing another username.

Sign-out clears in-memory account state and removes the persisted Auth session.
SQLite account history is retained to avoid discarding future unsynced edits;
the UUID mapping ensures subsequent sign-ins only load that account's rows.
New sign-ins and registrations require network access. Previously persisted
sessions can restore the matching local account while offline; cloud profile
operations remain unavailable until connectivity returns.

## Release blockers and deferred work

- **Account deletion is not available in the client.** The Settings action is
  intentionally hidden until a trusted Supabase Edge Function can verify the
  caller, require recent authentication, delete only that Auth user and
  cascading cloud data, and report cleanup failures. Do not expose an admin
  key or delete only the local SQLite row as a substitute.
- Verify confirmation/recovery redirects in the Supabase dashboard and native
  builds. Dashboard allowlists and email-template changes cannot be validated
  by the app test suite.
- Validate profile RLS with two real authenticated users and an anonymous
  client before release. SQL Editor/elevated credentials do not test client
  RLS behavior.
- Full history synchronization, offline write queues, account export, and
  cross-device conflict resolution remain tracked separately in #52.

Run `npm run typecheck`,
`npx jest services/__tests__/auth-validation-test.js services/__tests__/auth-storage-test.js services/__tests__/auth-links-test.js services/__tests__/supabase-profile-test.js --runInBand`,
and `npm run test:database`. A configured project is required for end-to-end
registration, email delivery, and two-user RLS checks.
